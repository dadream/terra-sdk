# 原生影像准备的额度与续作

本增量统一Direct-Wasm和Worker影像准备的申请/回执机制，并修复地形拒绝后
影像任务不再推进的唤醒遗漏。CBDAM、八根内部纹理树、外部TMS/WMTS适配、
1.25px目标、默认176160768字节预算和每轮32次拓扑变化保持不变。
这不是最低联合容量或完整P0–P4的完成声明。

本增量工程验收通过，提交和本机部署以证据目录的回执为准。先前2MiB的
3网格停滞定位到拒绝清理及粗化恢复吞掉真实容量变化，补充修复后定向往返
及完整门控通过；不将其扩展为全球最低容量或完整产品化完成。

## 两个已复现的问题

在`b16f4c6`上，以固定2MiB共享预算、真实Wasm、64像素图片及近零高程平面
从2网格推进到4网格。Direct已经显示符合1.25px的图片，却在影像准备未完成
状态等待30秒。原实现第一次额度拒绝就退出并重建准备，缺少真实回收等待和
明确短缺。记录见`native_joint_capacity_20261020/before/direct.json`。
Worker使用了带报价和回收等待的续作机制，但这不能保证另一个运行时入口等价。

统一额度以后，Worker的完整往返又暴露另一条停滞路径：地形准备暂停正在运行
的影像RPC并保留兼容输入；影像结果在`candidateEvaluating`期间到达，被直接
忽略。地形替换随后因容量拒绝，没有新切面触发影像更新，旧输入持续占用，
旧显示的计划也一直未完成。一次额外地形重试仍会失败，不能用定时重试补救。
记录见同目录`worker-roundtrip-cost.json`与`worker-manual-retry.json`。

## 实现边界

`adapters/wasm/imagery_grants.js`共用三种工作区的报价校验、真实额度申请、
一次异步回收等待和继续分发。Direct的`ImageryPreparation`同Worker一样先
返回工作区报价，持有现有准备游标等待实际回收；不以重建投影或调大预算争取空间。
底层独立ABI消费者仍可使用自己的账本，这不是旧运行时接口兼容层。

`LocalTerrainExecution.imageryTurn`跨合作式宿主轮次持有已授权的额度，直到
相应输入、引用索引或输出工作区确实完成。单个CPU切片、取消意图和相机变化
均不是释放凭据。实际分配先观测，再由同一`NativePayloadBudget`结束授权；
中间测量快照逐次释放。硬拒绝保留真实短缺，交给原有粗化/容量恢复流程。

地形准备期间无法接纳的影像结果现在留下`imageryRefreshPending`。地形事务
结束后，无论新切面成功还是拒绝，均恢复当前合法切面的影像工作。它不提前
替换显示，不伪造GPU回执，也不依靠不断重试地形释放其他所有者的输入。

C ABI46、Worker46和Wasm字节未变；这是宿主额度与任务唤醒修复。

首次完整发布又暴露Direct的暂停入口原为空实现。共用额度分发后，一个调用
可以跨多次工作区授权；地形等待它结束时，整个运动阶段可能没有新网格。
本地现在以独立的操作标记结束当前调用，在下个有界切片关闭该调用尚未完成的
授权，保留兼容准备；硬取消仍清理任务。测量投递也读取同一标记。旧的失败
模块在主动暂停合同中失败；当前实现及最终完整运动场景通过，结果见文末。

完整候选事务在开始前记录实际占用及可用版本，在最后一个清理动作后确定
等待起点。归还本次临时额度不应触发同一失败；清理期间若释放了此前仍被
占用的旧载荷，应保留这次真实变化，让原有调度重新尝试准入。
`capacity_refusal.js`比较事务前后净占用，不预约容量或保证重试成功；实际
分配仍走原有完整报价、额度和回执。

账本以常数时间维护`disposableBytes`，排除本来已经可回收的数值memo，避免
重建/清理可选缓存制造假唤醒。计数在创建、大小变化、移交和释放处更新，
独立测试以实际活跃租约逐项求和核对，包括最大安全整数移交。

## 验证与限制

`tests/js/local_imagery_grants_test.js`覆盖输入、引用和输出三种额度的完成、
取消、软暂停、硬拒绝和原生失败：扣住回收及多个宿主轮次，验证游标保留、没有空转、
授权不提前退款，最后归零。合同有独立期限并排空受控的异步任务。

`tests/js/imagery_terrain_resume_contract.js`经过实际运行时的影像和地形入口，
分别扣住Direct完成结果及Worker暂停结果，再拒绝地形后继。验证旧显示保留、
影像恢复及其输入只在完成时归还。精确`b16f4c6`运行时在此合同失败，反证见
`old-runtime-negative.json`与对应日志；不是人为删除一行构造的旧实现。

`tests/wasm/native_imagery_recovery_contract.js`执行实际Direct和Worker的
`0→1→0→1→0`平面网格往返，全程固定2MiB。使用GL夹具检查渲染器提交调用、
完整规划、目标达标及状态无缺图，不能只凭已有画面的误差达标结束；每站仍限30秒。暂时容量
拒绝允许进入正常恢复，但必须报告正整数短缺，最终不能留下容量阻塞；这与
把容量诊断当引擎失败不同。销毁后账本和资源计时器归零。

定向通过记录在`viewer_verify_output/native_joint_capacity_20261020/`。
首次冻结676份输入通过完整19项baseline、编译警告0；发布在Direct故障网络
斜视的运动进展断言失败，3秒内一次发布但网格变化0，尽管最终精度达标。
失败、当时源码、基线和控制面清理保留在`before-direct-suspension/`。

补充暂停后，可控额度和运行时合同通过，但`roundtrip-soft-suspend.log`保留
真实Worker的30秒失败：当前影像已完成，目标4网格只呈现3网格，联合容量
恢复未结束。`worker-model-trim.json`对该停滞执行一次显式闲置模型回收，实际
释放0，不能据此把原因认定为遗漏了闲置模型回收。报价后的占用、清理后的
可用空间及重试条件随后在同一事务中核对；没有增加预算或定时重试来掩盖问题。

后续`capacity_refusal_contract.js`分别经过共享候选事务和直接ABI读帧路径，
验证临时额度、可选memo和最后清理释放旧载荷三种情况。精确旧候选模块在
最后一种情况失败，新实现六种情况通过，见`old-capacity-epoch-negative.json`。
`native-capacity-checkpoint.log`的实际Direct/Worker固定2MiB完整往返通过，
每站约64–456ms，精度约1.171875px；不是全球最低容量或真实浏览器时延证明。

运行时还必须在粗化恢复结束后再确认已经消费这次容量变化。否则没有拓扑
变化的恢复轮次会取走唯一唤醒，物理候选仍不尝试。`capacity_wake_contract.js`
经过真实运行时验证一次真实退款、一次不变粗化及随后的物理发布；精确旧
运行时仅尝试一次物理更新并失败，新实现尝试两次并恢复，见
`old-coarsening-wake-negative.json`。原来无新容量的拒绝仍须停等。

最终679份冻结输入通过完整19项baseline和SDK发布，编译警告0；发布driver
从Native阶段一次退出0，CMake构建来自同一冻结实现的完整baseline。Chrome155
Intel Vulkan浏览器366项/12条可见轨迹通过，采样白屏/缺图及三组网络轨迹
全程引擎错误均0；销毁后的占用、请求和计时器归零。原1次预热加2次测量的
24份堆容量样本均25493504字节，第二测量圈零增长要求保持。148个实际压缩
模块/Worker、Native安装4项及两个归档分别核对，不以源码测试代替分发核对。

Direct故障斜视的3秒运动内6次发布、4次网格变化；四组大倾角停稳仍需
13.6–20.5秒。固定真实地形回放及合成图片不能证明真实天地图、DOM输入到
像素响应、移动设备或工业级30FPS目标。提交、本机18766更新及控制面清理
结果以同目录`deployment.json`、`cleanup.json`为准；49未部署。

平面夹具不证明全球山地不可分替换组、默认预算最低值、真实图源或移动设备
性能。完整元数据计量、大倾角长尾、固定工作量归因和P0–P4继续独立验收。
